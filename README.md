# Fraud Detection Console

A local-first fraud operations console using real dataset accounts, FastAPI, Next.js, cloud databases, and Gemini-backed investigation agents.

| Surface | URL |
| --- | --- |
| Web console | https://fraud-detection-console.vercel.app |
| Backend API | https://fraud-detection-api-nijg.onrender.com |
| Health check | https://fraud-detection-api-nijg.onrender.com/health |

Hosted services may take a moment to wake up on free tiers.

## Runtime Model

The main workflow is `DEMO_MODE=false`:

- Redis Cloud powers Phase 1 risk scores, velocity, whitelist, and blacklist checks.
- Neo4j AuraDB stores account, device, IP, and transfer graph evidence.
- MongoDB Atlas stores customer profiles and transaction history.
- ChromaDB Cloud stores fraud knowledge and prior investigation patterns.
- Gemini drives Planner, Executor, Vision, Report, and Detective agents.

`DEMO_MODE=true` remains only for deterministic tests and offline fallback behavior.

## What It Does

- Phase 1 screens transactions with dataset-scale rules, Redis signals, shared infrastructure, and balance-drain checks.
- Phase 2 investigates yellow cases through agent-planned DB queries and evidence analysis.
- Phase 3 returns `allow`, `block`, or `escalate`, then writes audit/risk updates.
- The UI presents a two-column banking simulator and fraud operations console with live SSE pipeline events.

## Dataset

`final.csv` is **not** a real banking dataset and is not presented as one.

| Layer | Origin |
|---|---|
| `step, type, amount, sender/receiver balances, isFraud` | PaySim, the standard synthetic fraud benchmark |
| `device_id, ip_address, geolocation_*, auth_method` | Generated by `evaluation/regenerate_dataset.py` |
| Additional transaction rows | Generated, marked `row_source=synthetic_activity` |

PaySim is itself synthetic by design, because real transaction data cannot be
published. **No real customer data is involved at any point.**

### The dataset used to be trivially separable

The first version decided the label first and then wrote the enrichment to look
guilty. The result:

| Rule | Precision | Recall |
|---|---:|---:|
| `auth_method == 'SMS_OTP'` | **1.000** | 0.886 |
| account has > 2 transactions | **1.000** | 0.673 |
| device or IP seen more than twice | **1.000** | 0.748 |
| `SMS_OTP or first-seen device` | **1.000** | **0.995** |

That last line is a two-line rule scoring **F1 = 1.000 on the published
holdout**, against 0.883 for the agent pipeline. Every model result on that data
was meaningless, and the "recall goes to 1.0 without the LLM" symptom came from
here, not from the evaluation method.

### What the generator does now

Enrichment is drawn from behaviour and bank policy, and the label only shifts
probabilities:

- `auth_method` follows the amount tier a bank would require, with a mild tilt
  toward the weakest channel for fraud. SMS_OTP now runs **1.4x** the base rate
  instead of 100%.
- Devices and addresses come from per-account pools. Mule rings share
  infrastructure and so do households, so a device used by more than 3 accounts
  runs **2.4x** the base rate — evidence worth investigating, not proof.
- Legitimate accounts were given transaction histories, because previously every
  account with 3+ rows was fraudulent.
- Some fraud accounts were given clean history first, which is what account
  takeover looks like. 455 of 456 accounts used to be entirely one or the other.
- Added rows carry PaySim's class balance. An earlier attempt added only
  legitimate rows; because generated rows are somewhat detectable, a model then
  reached **F1 = 1.000** by recognising the generator rather than the fraud.

All 202 real PaySim fraud rows are preserved. Regeneration is seeded and
reproducible:

```powershell
python evaluation\regenerate_dataset.py --seed 42
python evaluation\audit_leakage.py --check
```

### Leakage audit

`evaluation/audit_leakage.py` scores every feature on its own and fails the
build if one gives the label away. PaySim columns are held to the giveaway gate
only — real fraud genuinely concentrates in TRANSFER and genuinely targets empty
accounts, and destroying that would make the data less realistic, not more.

It also trains a detector to tell generated rows from PaySim rows, because the
single-feature view cannot see a combination.

### Known limits

- **Fraud rate is 28.9%.** Real PaySim is ~0.13%. This is a curated,
  rebalanced subset, so precision figures are far more optimistic than
  production would be.
- **Account persistence is high.** An account that committed fraud in the train
  split usually does so in the holdout. Evaluation therefore reports
  seen-before and first-seen accounts separately.
- **The holdout has 83 fraud rows.** Confidence intervals are wide; point
  estimates alone should not be trusted, which is why every number below carries
  one.
- Properly fixing the sampling would mean re-drawing from the full PaySim
  dataset on Kaggle rather than augmenting this subset.

## Benchmark

The benchmark that matters is the temporal holdout: the first 70% of `final.csv` is used as historical memory, and the last 30% is evaluated as future transactions.

### Tabular baselines

The question to answer before claiming anything for an LLM pipeline is whether
it beats a model that trains in two seconds. Same data, same temporal split,
bootstrap confidence intervals over 10,000 resamples:

| Model | Precision | Recall | F1 | 95% CI (F1) |
|---|---:|---:|---:|---|
| **Gradient boosting** | 0.8941 | 0.9157 | **0.9048** | [0.8550, 0.9474] |
| Logistic regression | 0.6061 | 0.9639 | 0.7442 | [0.6734, 0.8054] |

Split by whether the account appeared in the train window:

| | n | fraud | Precision | Recall | F1 |
|---|---:|---:|---:|---:|---:|
| Seen before | 145 | 47 | 0.9375 | 0.9574 | 0.9474 |
| First seen | 168 | 36 | 0.8378 | 0.8611 | 0.8493 |

Catching a known mule says little about what an investigation agent adds; the
first-seen column is the one that matters.


Run or resume the real benchmark:

```powershell

python evaluation\evaluate_real_resume.py --push-cloud-train --reset-progress --max-new-yellow 5

# Later runs: resume from the checkpoint. Do not reseed cloud DBs.
python evaluation\evaluate_real_resume.py --max-new-yellow 5
```

`evaluate_real_resume.py` writes `evaluation/results/real_llm_resume.json` after every successful transaction. Metrics are emitted only when `completed_rows == holdout_rows`.

## Real-Service Notes

- `AUTO_SEED_ON_STARTUP=false` is recommended for daily local work. It prevents the API server from wiping/reseeding cloud DBs every time it starts.
- `python evaluation\push_seed_data.py` is the full-dataset seed path for the local UI demo.
- `DEMO_MODE=false` still has graceful fallback per service. If one cloud service fails, the API can continue, but `/health` will reveal which component fell back.
- Fallback caches are hydrated from the real dataset at startup, so a temporary cloud failure still uses `C...` dataset IDs instead of old `ACC_*` demo data.
- MongoDB Atlas `SSL handshake failed` / `TLSV1_ALERT_INTERNAL_ERROR` usually means the current public IP is not allowed in Atlas Network Access.
- Normal Gemini calls are serialized and retried to reduce free-tier quota pressure. The resumable real benchmark uses strict mode, so quota/API errors stop the current run and keep the last saved checkpoint.
- The project currently uses the deprecated `google-generativeai` SDK. It still works, but migrating to `google.genai` is the next maintenance step.
